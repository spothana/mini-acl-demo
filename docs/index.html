How acl_classify()
matches a packet

A standalone reimplementation of the DPDK Access Control library's core ideas. This page animates the one operation that matters: taking a packet, testing it against every rule, and resolving the highest-priority match for each category — all in a single pass.

01The classification loop

Press Run to send a packet through the rule set.

A packet is an N-tuple — here a 5-tuple of protocol, source/destination IP, and source/destination port. Each rule declares a value (or range, or bitmask) for every field. The packet matches a rule only when all of its fields pass. Among the rules that match, the one with the highest priority wins each category it serves.

02The three field types

Each rule field is tested by one of three comparisons.

Every field definition picks a type, and that type decides what its two numbers — value and range — actually mean: 

/* MASK — value + prefix length. Built for IP addresses. */
192.168.0.0/16   matches  192.168.*.*       // compare top 16 bits

/* RANGE — an inclusive [low, high] interval. Built for ports. */
[1024, 65535]     matches  any port >= 1024

/* BITMASK — value + a mask selecting which bits to check. */
value=6 mask=0xff  matches  protocol 6 (TCP) exactly

03Parallel category lookup

One search, many answers.

Each rule carries a category_mask. A single acl_classify() call returns one result per category — so a firewall rule set, a routing rule set, and a QoS rule set can live in one context and all be resolved together. In the animation above, watch the four result cells fill independently: different rules can win different categories for the very same packet. 

/* the call — keys in, one result per category out */
uint32_t results[4];
acl_classify(ctx, keys, 1, results);

/* packet from 10.1.1.1 to 192.168.1.15 yields: */
results = { 2, 3, 0, 0 };
//           cat0 cat1 cat2 cat3   — 0 means no match

04Where DPDK goes faster

The shape we simplified away.

This library does a linear scan — clear, but O(rules) per packet. The real DPDK library compiles the rule set at build() time into multi-bit tries (stride 8) so a lookup walks a few bytes instead of every rule. It also splits rules into non-intersecting subsets to bound memory:

rule set │ ├─ build() ── compile ──▶ trie A (subset 1) │ trie B (subset 2) │ trie C (subset 3) │ └─ classify() walks tries 8 bits at a time, SIMD-parallel across many packets

The observable behaviour is identical — same matches, same priority resolution, same per-category results — which is exactly why this project can reproduce the documentation's {2,3,0,0} output without any of the trie machinery.
